Approach

Product judgment backed by systems work

I started by building and operating a local commerce product, moved into campaign operations, then spent four years translating banking workflows into services, APIs, data models, and release requirements for engagements serving HSBC Bank and Saudi National Bank.

That path matters because AI products fail for ordinary reasons: unclear ownership, weak data, missing states, unsafe actions, and no plan for failure. I work across the product and technical layers so those questions are answered before a demo becomes an operating problem.

For high-risk workflows, I add citations, validation, permissions, audit records, fallbacks, and human approval. The goal is a useful system that people can understand and operate, not a black box with an impressive prompt.

01 · Frame

Find the decision and the user

Map the workflow, source material, constraints, failure cost, and the smallest release worth testing.

02 · Build

Connect product logic to the system

Write the requirements, architecture, data contracts, interfaces, evaluation rules, and working implementation.

03 · Prove

Test the states, not just the happy path

Check failure behavior, permissions, evidence, release controls, and the boundary between working and planned.
